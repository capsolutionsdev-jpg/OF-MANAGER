### 1. SYNTHÈSE EXÉCUTIVE

La plateforme est **structurellement saine côté produit livré** : le pipeline CI bloque réellement sur lint + types + tests (dont l'isolation multi-tenant) + build ; les en-têtes de sécurité HTTP (CSP, HSTS `preload` 2 ans, anti-clickjacking) et le TLS Let's Encrypt sont **vérifiés servis en production** ; le socle est **100 % UE** (Vercel `fra1` + Neon Francfort + Upstash UE) ; les secrets tenant sont chiffrés AES-256-GCM *fail-closed* ; aucun `.env` n'a jamais fuité dans Git ; les crons sont authentifiés.

Le problème n'est pas le produit, c'est **la chaîne d'exploitation autour**. Trois blocages : (1) **aucune séparation dev/prod** — le poste de développement utilise la **base ET les secrets de production** (dont la clé maîtresse qui déchiffre les clés API de tous les OF) ; (2) le **schéma de prod est modifié à la main par `prisma db push`** sur la base partagée, sans migration versionnée depuis ~12 semaines, donc **sans rollback ni reconstruction possible** ; (3) tous les **documents (pièces d'identité, dossiers candidats, conventions, factures) sont stockés en Vercel Blob PUBLIC**, accessibles par URL sans authentification et de façon permanente. S'y ajoutent l'absence de supervision/alerting activée, de traçabilité de version, de procédure de rollback, et un plan Vercel à confirmer (usage commercial + 8 crons imposent Pro).

**VERDICT : GO CONDITIONNEL**
La plateforme *live* est saine et les blocages sont tous corrigeables avec une charge bornée ; aucune refonte n'est requise. Le passage en clientèle payante est conditionné à la levée des **4 conditions P0** : (C1) isoler le dev de la prod — base **et** secrets ; (C2) restaurer un chemin de migrations versionnées avant tout nouveau changement de schéma ; (C3) mettre les documents sensibles derrière un contrôle d'accès (ou acter un risque résiduel documenté) ; (C4) confirmer le plan Vercel Pro + activer suivi d'erreurs et sonde de disponibilité. Sans levée, le verdict bascule en NO-GO.

### 3. FICHES DÉTAILLÉES (toutes les 🔴 et 🟠)

#### A08-001 — Aucune séparation dev/prod : le poste de dev utilise la base ET les secrets de production — 🔴
- **Constat :** il n'existe aucun environnement intermédiaire entre le poste de développement et la production. Le `.env` local pointe la base Neon **de production** et contient les **mêmes secrets** que la prod (dont la clé maîtresse de chiffrement). Deux facettes d'une même défaillance structurelle (contrôles étanchéité **et** séparation des secrets).
- **Preuve :**
  - *Facette données* — `scripts/reset-data.ts:10-14` (aveu en clair) : « Il n'est PAS scopé par tenant et, la base de dev pointant aujourd'hui la prod, une exécution accidentelle serait catastrophique. » `.env.example:6` n'est qu'une recommandation non contrainte (« dev ≠ prod : utiliser une branche de test ») ; `DATABASE_URL_TEST` est `[OPT]` et **vide** dans le `.env` local. Seul autre environnement hors-prod = la base éphémère du CI (`ci.yml:15-32`).
  - *Facette secrets* — lecture masquée du `.env` local (chef de projet + spécialiste, indépendamment) : `DATABASE_URL`/`DIRECT_URL` → host `ep-steep-****.eu-central-1.aws.neon.tech` (= host prod, cf. historique projet), `neondb_owner`, mot de passe `npg_****` en clair ; `AUTH_SECRET`, `SECRETS_ENCRYPTION_KEY`, `CRON_SECRET`, `LEAD_API_SECRET`, `SUPERADMIN_PASSWORD`, `RESEND_API_KEY` réelle tous en clair. En-tête du fichier : « Secrets générés le 2026-08-20 : à **REPORTER À L'IDENTIQUE dans Vercel** (surtout SECRETS_ENCRYPTION_KEY + AUTH_SECRET) » → ce sont bien les valeurs de prod. `src/lib/crypto.ts:13-16` : `SECRETS_ENCRYPTION_KEY` dérive la clé AES-256-GCM qui déchiffre **toutes** les clés API tenant.
- **Scénario d'impact :** (a) un `npm run dev`, un script `seed-*`/`reset-data`, un test ou un `db push` lancé en local écrit dans les données de production de **tous les OF** ; (b) une compromission du poste (vol, malware, synchro cloud du `.env`) donne à l'attaquant la forge de sessions (AUTH_SECRET), la base réelle, l'API Resend, et surtout le **déchiffrement de toutes les clés API des clients** (SECRETS_ENCRYPTION_KEY) — sans possibilité d'isoler l'incident sans rotation prod complète.
- **Cause racine :** le fork a été bootstrapé le 20/08 en pointant directement la base et les secrets de prod (rapidité de mise en service), sans jamais créer d'environnement de dev/préprod isolé.
- **Recommandation :** créer une **branche Neon de dev/préprod** (schéma copié, données synthétiques) et y pointer le `.env` local ; générer des `AUTH_SECRET`/`SECRETS_ENCRYPTION_KEY`/`CRON_SECRET` **locaux distincts** ; retirer la `RESEND_API_KEY` réelle (mode démo). Réserver les secrets prod à Vercel. Considérer les secrets actuellement sur le poste comme potentiellement exposés → **rotation** selon `docs/ROTATION-SECRETS.md` (« Après une fuite de copie .env », ordre base→auth→chiffrement→intégrations).
- **Charge :** M — **Priorité :** P0 — **Type :** Chantier
- **Vérification de la correction :** `.env` local dont `DATABASE_URL` pointe une branche Neon ≠ prod ; `AUTH_SECRET`/`SECRETS_ENCRYPTION_KEY` locaux ≠ Vercel ; un `git grep` d'un secret prod dans l'environnement local ne renvoie rien ; rotation consignée.

#### A08-002 — Schéma de prod piloté par `prisma db push` manuel — migrations figées, pas de rollback — 🔴
- **Constat :** le schéma de production évolue par `prisma db push` exécuté à la main sur la base Neon partagée. Aucune migration versionnée depuis le 5 juin, alors que le schéma a fortement évolué (Stripe, RGPD, sièges, unicité multi-tenant…). L'historique `prisma/migrations/` ne permet plus de reconstruire la base à l'identique.
- **Preuve :** dernière migration = `prisma/migrations/20260605140000_elearning_v2` ; `prisma/schema.prisma` (112 Ko) modifié le 28/08 → ~12 semaines de dérive. `docs/MIGRATIONS.md:3-8` l'atteste explicitement (« ne permet plus de reconstruire la base à l'identique… pas de rollback de schéma »). `docs/DEPLOIEMENT.md:89-91` **prescrit** le procédé : « Les changements de schéma : `npx prisma db push` (…) jamais `migrate dev` ». Nuance de la vérification adversariale : `--accept-data-loss` n'apparaît que dans le CI (`ci.yml:52`, base éphémère) ; en prod le `db push` est nu (refuse par défaut les changements destructifs) — la perte de colonnes n'est donc pas strictement « silencieuse », mais l'absence de réversibilité et de traçabilité demeure.
- **Scénario d'impact :** un `db push` appliqué sur la base partagée modifie instantanément le schéma de **tous les tenants**, sans revue ni trace ; en cas d'erreur, **aucun rollback de schéma** n'existe (pas de migration *down*), et une reconstruction à l'identique (restauration, nouvel environnement, preuve d'audit) est impossible. Un décalage schéma↔code (schéma poussé avant/après le déploiement) peut casser tous les tenants.
- **Cause racine :** contournement historique de `migrate dev` (jugé risqué sur base partagée), jamais rebasculé vers un flux versionné.
- **Recommandation :** exécuter la re-baseline **déjà outillée** (`docs/MIGRATIONS.md:16-37` + `docs/db-baseline.sql`) sur une branche Neon de test, puis adopter `prisma migrate deploy` (migrations versionnées, réversibles, tracées) et **bannir `db push` en prod**. Intégrer l'étape de migration au flux de déploiement (hors requête, sur `DIRECT_URL`, avec revue).
- **Charge :** L — **Priorité :** P0 — **Type :** Chantier
- **Vérification de la correction :** `prisma/migrations/` contient une baseline + les migrations postérieures ; `prisma migrate status` = « up to date » sur prod ; un `db push` en prod n'est plus documenté ni pratiqué.

#### A08-003 — Vercel Blob en accès PUBLIC pour tous les documents PII — 🔴
- **Constat :** l'unique fonction d'upload stocke **tous** les fichiers en Vercel Blob avec `access:"public"` et renvoie une URL publique, pérenne et sans authentification. Sont concernés des documents personnels sensibles : pièces du dossier candidat, pièces d'identité scannées, conventions signées, factures.
- **Preuve :** `src/lib/blob.ts:17-24` — `put(..., { access:"public", addRandomSuffix:true })` → `return blob.url` (commentaire : « URL publique pérenne »). Source **unique** de 12 flux de prod : `dossier-actions.ts:151`, `dossier-b2b-actions.ts:31`, `facture-actions.ts:60`, `formateur-actions.ts:129`, `convention-signature-actions.ts:27`, `scan-actions.ts:53`, `expression-besoin`, `publish.ts:50`, `publish-auto.ts:57`, `convention-pdf.ts:162`, `api/upload/route.ts:30`. #### A08-010 — `www.ofmanager.info` cassé (IPv6 → parking OVH, IPv4 → cert TLS invalide) — 🟠
- **Constat :** le sous-domaine `www` est mal configuré : en IPv6 il résout vers l'infrastructure OVH (page de parking Apache), en IPv4 il atteint Vercel mais présente un certificat qui ne couvre pas `www`. L'apex `ofmanager.info` (canonique) fonctionne, lui, correctement.
- **Preuve (vérifications live du chef de projet) :**

  - Par contraste : apex `ofmanager.info` A `76.76.21.21`, en-têtes app + cert Let's Encrypt valides (cf. section 4).
- **Scénario d'impact :** un prospect qui saisit `www.ofmanager.info` (réflexe courant) obtient soit un **avertissement de sécurité du navigateur** (IPv4), soit une **page de parking OVH** (IPv6, souvent préféré par *Happy Eyeballs*). En phase de pré-commercialisation auprès de 3 OF prospects, c'est une atteinte directe à la confiance et à l'image, pour un correctif trivial.
- **Cause racine :** enregistrement AAAA OVH résiduel non nettoyé sur `www` + `www` non déclaré/vérifié comme domaine sur Vercel (pas de SAN dans le certificat).
- **Recommandation :** supprimer l'AAAA OVH sur `www` ; déclarer `www.ofmanager.info` dans **Vercel → Domains** (redirection 308 vers l'apex, méthode recommandée) via un `CNAME www → cname.vercel-dns.com`. Vérifier ensuite `curl -I https://www.ofmanager.info` en IPv4 **et** IPv6.
- **Charge :** S — **Priorité :** P1 — **Type :** Quick win
- **Vérification de la correction :** `www` redirige (308) vers l'apex avec un certificat valide, en IPv4 comme en IPv6 ; plus aucune réponse `Server: Apache`.
